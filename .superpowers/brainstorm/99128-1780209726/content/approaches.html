Animation Sandbox — Architecture Approaches

How to structure the sandbox directory and its relationship to the main battle UI

A

Next.js Route Sandbox (Recommended)

Add /sandbox/animations route inside the existing Next.js app. Reuses the real BattlefieldView, TroopSprite, and sprite assets. A control panel triggers animations with mock game data.

Pros

  • Uses real components — animations transfer directly to production
  • Access to all existing sprites, styles, and Tailwind config
  • No separate build step or dev server
  • Easy to share — just visit /sandbox/animations on the dev server

Cons

  • Sandbox code ships in the bundle unless excluded in production build
  • Tied to Next.js — can't iterate without the full app running
B

Standalone Vite Playground

A separate frontend/sandbox/ directory with its own vite.config.ts. Imports animation modules from the main app but renders in a minimal harness — no Next.js overhead.

Pros

  • Instant HMR — Vite is faster than Next.js for pure component iteration
  • Clean separation — sandbox never pollutes production bundle
  • Can be a plain React app or even vanilla JS + anime.js

Cons

  • Needs its own build config, duplicates some setup
  • Must manually keep sprite paths and shared types in sync
  • Components may need shimming (Next.js Image → plain img)
C

Hybrid — Next.js Route + Extracted Animation Library

Create frontend/src/lib/animations/ as a pure animation library (no React deps). The sandbox is a Next.js route that composes these with the battlefield. Production components import from the same library.

Pros

  • Clean architecture — animations are testable functions, not component internals
  • Sandbox uses real components for preview
  • Animation logic can be unit tested without rendering

Cons

  • More upfront structure before you can start playing with effects
  • Abstraction may be premature until you know which animations stick
